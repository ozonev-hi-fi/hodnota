- [ ] Implement the remaining first-release providers — separate feature branch per provider, merged to `develop` one at a time; expect one shared ADR covering the common decisions across them (most of the per-provider architecture — endpoint style, catalog dedup, temp-candidate caching — was already settled in [decisions/0008](decisions/0008-youtube-search-sharepage-skeleton.md)), written when work on the first of these starts, not preemptively. That ADR is [decisions/0011](decisions/0011-spotify-provider-and-cross-provider-result-merging.md) — written when Spotify (the first of these) started, and it also covers cross-provider search-result merging, since adding a second provider without merging would show the same song once per platform.
  - [x] Spotify — implemented, but disabled since Spotify now requires an active Premium subscription on the app-owner's account to use the Web API at all; the project owner won't pay for one, so this runs dormant (config-optional, not fail-fast) until that changes — see [decisions/0011](decisions/0011-spotify-provider-and-cross-provider-result-merging.md)'s addendum.
  - [x] Qobuz — implemented (config-optional, like Spotify, since Qobuz has no self-serve developer portal). Working locally with a dev `app_id` and a dev user auth token (search requires both), but official credentials must still be requested from `api@qobuz.com` before this can ship to real users, see the UAT-gate ToS review item below.
  - [x] Discogs — implemented as a regular `IStreamingProvider` after all (see [decisions/0012](decisions/0012-discogs-provider.md)): `StreamingSearchResult`/`ProviderLinkCandidate` were already metadata/link-shaped, not playback-shaped, so no new interface was needed. Album searches only (the search request gained a required Song/Album type): links to the Discogs master when one exists, otherwise to the specific release; no Discogs link on track share pages, and no UPC taken from Discogs; artist-only matches are dropped, not approximated — adding a `StreamingResultType.Artist` case is named as deliberate follow-up work, not forgotten. Self-serve Personal Access Token auth, fail-fast like YouTube (no Spotify/Qobuz-style access gotcha found). Ranked first in `ProviderTrustOrder`, above Qobuz. Ships with a required "Data provided by Discogs" attribution credit on the share page and under search results now, not deferred to the general provider-ToS-review item below, since it's a condition of API access rather than a presentation style choice.
  - [x] Tidal — implemented as a regular `IStreamingProvider` (see [decisions/0013](decisions/0013-tidal-provider.md)): hand-written `HttpClient` client with the Client Credentials flow and JSON:API response mapping; song and album search, both ISRC (tracks) and UPC (albums) filled in. Self-serve free developer credentials, fail-fast like YouTube/Discogs. Ranked after Qobuz. Ships with a plain-text "Content provided by TIDAL" credit on the share page and under search results, since a TIDAL credit linked back to the service is a condition of API access; the logo requirement is not met yet and stays with the ToS-review item below.
  - [ ] Deezer
  - [ ] Apple Music
  - [ ] Bandcamp — selling platform with limited preview playback (1-2 plays/track); not a full `IStreamingProvider`, but still produces a shareable link. Interface shape decided when this item is picked up.
- [ ] Resolve-time catalog enrichment — decided in [decisions/0014](decisions/0014-resolve-time-catalog-enrichment.md) (the notes below are the original brief; the ADR supersedes them where they differ). Search only helps the user find an item; after they pick a result, look it up again on every provider and build one verified catalog entry that later visits reuse. Picked up before Deezer, Apple Music and Bandcamp, so those are built with lookup support from the start. See [decisions/0012](decisions/0012-discogs-provider.md)'s "Out of scope" section.
  - Today: `POST /api/catalog/resolve` saves the cached search row as it is, with no new provider calls, so a share page only carries links from providers whose result matched the same normalized artist + title (`SearchResultKey`) during that one search.
  - Matching: strict, ISRC (tracks) / UPC (albums) first, normalized artist + title only as a fallback. Both keys are already stored, but never used to confirm a cross-provider match.
  - Discogs: search by the other providers' UPC (`barcode`, digits only, 12/13-digit check), then follow the release's `master_id` to the master page, otherwise keep the release page. This also finds master-less releases that search rarely shows today (the release request only runs when fewer than 5 masters match), and can give masters a real release type (they always get `Album` today).
  - YouTube: no ISRC/UPC, and album playlists are free-text titles from any channel, so a strict match needs YouTube-specific rules (e.g. prefer official "Artist - Topic" channels and YouTube Music album playlists). No link is better than a wrong one — the same bias as [decisions/0011](decisions/0011-spotify-provider-and-cross-provider-result-merging.md)'s merge rules.
  - Track share pages: decide whether a track links to its album's Discogs master (no Discogs link today).
  - Reuse: `EfCatalogRepository.CreateSharePageAsync` already reuses the catalog track/release when any of the clicked row's links is already stored, but still creates a new share page on every resolve — reuse the existing share page too.
  - Trust order: split `ProviderTrustOrder` into a catalog-authority order (whose metadata wins when providers disagree on an artist name, release date, etc. — extends [decisions/0007](decisions/0007-catalog-data-model.md)'s data model and [decisions/0008](decisions/0008-youtube-search-sharepage-skeleton.md)'s exact-match dedup) and a search-display order (which rows come first). Working hypothesis: Discogs first for release/artist metadata.
  - Open questions for the ADR: waiting time on click (one extra call per provider), what to store when a provider finds nothing, and rate limits (Discogs: 60 requests/minute).
- [ ] YouTube and YouTube Music: find the real album or song, not a pirate upload — `search.list` ranks any upload by text, and the official album playlists are not reachable through it. Investigation, options with their ToS risk, golden test cases and a phased fix plan: [youtube-music-search.md](youtube-music-search.md). Phase 0 (accept only the artist's own or "Topic" channel) is done; the rest waits for the live experiments and the decisions D1–D5 in that document, which become an ADR.
- [ ] Scheduled catalog refresh — a background job that re-checks existing provider links from time to time (is the release/track still on the service?) and re-checks "not found" platforms more often (has it appeared?), using the check dates saved by [decisions/0014](decisions/0014-resolve-time-catalog-enrichment.md). Users keep getting the existing share page without new provider calls; the catalog updates in the background. Needs a scheduler, which may settle 0014's open background-runner question.
- [ ] User-suggested links — a share-page viewer suggests a link instead of, or in addition to, an existing one; hodnota checks that the link is valid and fits the page before adding it. The "not found" row on the share page is the natural place for the button.
- [ ] Several versions per platform — services often have the original, a remaster, and reissues of one release; the share page should show all of them. Real example: Metallica's *Load* has two official YouTube Music album playlists (`OLAK5uy_nn9_UEJTyKvU65JlglPBRMp9eWyxOTFWc` and `OLAK5uy_nf8K8yHuLThX0qvPGCIM2eBKndPale4vU`); until this item is done the page shows one of them. Needs the one-link-per-platform unique index from [decisions/0007](decisions/0007-catalog-data-model.md) to change.
- [ ] Catalog-first search — search shows matching catalog items first, so users pick an existing item instead of searching the providers again and reaching the same share page.
- [ ] Add observability: structured logging conventions + basic error/crash alerting — no dependency on the hosting choice below; a documentation gap surfaced by an SDLC audit, see [decisions/0010](decisions/0010-uat-production-readiness-gate.md).
- [ ] Choose and add a `LICENSE` file — before first real release/deployment, not before (repo is public now with no LICENSE, which defaults to "all rights reserved" — the safe side of the ambiguity, so no urgency). Goal is source-available but restricted against commercial use by others, not necessarily OSI-approved "open source" — plain AGPL-3.0 doesn't fit since it still permits commercial use (only requires sharing modifications). Candidates being weighed, decision still open: CC BY-NC-SA 4.0 (Creative Commons explicitly advises against using CC licenses for software — no patent handling, poor fit), PolyForm Noncommercial (built for source-available non-commercial software), Business Source License/BUSL (time-delimited commercial-use restriction that converts to a real OSS license later — used by MariaDB, Sentry, CockroachDB; may suit a scenario where investors/commercialization enter the picture later).
- [ ] Figure out hosting — must be free (or effectively free) to start.
- [ ] Backup & disaster recovery plan — depends on the hosting choice above; promotes the aspirational mention in [architecture.md](architecture.md)'s Hosting section into real, tested work, see [decisions/0010](decisions/0010-uat-production-readiness-gate.md).
- [ ] Integrate email service
- [ ] Use email service for auth confirmation flows — also a practical prerequisite for UAT itself (see below), since `RequireConfirmedAccount = true` blocks any invited tester from confirming an account without it.
- [ ] Define UAT / production-readiness gate — privacy policy published + human security review (incl. CSP, secure headers, secure cookie attributes if token storage ever moves off `localStorage`, rate limiting on anonymous endpoints — the share-page event stream added by [decisions/0014](decisions/0014-resolve-time-catalog-enrichment.md) can queue provider calls for anyone with a page id) as acceptance criteria before opening real public registration; see [decisions/0010](decisions/0010-uat-production-readiness-gate.md).
- [ ] Implement auth (Google/Facebook external login)
- [ ] Third-party streaming-API terms-of-service review (YouTube, Spotify, Qobuz, Tidal, Deezer, Apple Music, Bandcamp, Discogs) — deliberately after the UAT gate above, non-blocking for a non-commercial pre-release project, see [decisions/0010](decisions/0010-uat-production-readiness-gate.md). Spotify and Discogs added to this list after ADR 0010 was accepted — the ADR's own provider enumeration reflects the roster at the time and is left as historical record. Must cover UI-presentation rules (logo usage, attribution, linking back), not just API-usage terms — Spotify's Developer Policy is more prescriptive about presentation than YouTube's; [decisions/0011](decisions/0011-spotify-provider-and-cross-provider-result-merging.md) responded by keeping the pre-UAT UI deliberately neutral text (no logos, no brand colors, no platform-styled buttons) precisely so this review cannot force a redesign of work already shipped. Tidal needs its own explicit check here too: its Developer Terms allow non-commercial applications only (a constraint on the open LICENSE question above) and its guidelines ask for the TIDAL logo next to TIDAL content, which the text-only credit does not satisfy; its developer platform is also still in Beta and changed its search contract without notice once already. Qobuz needs its own explicit check here: unlike YouTube/Spotify, it has no self-serve developer portal, and official `app_id`/`app_secret` must come from a manual request to `api@qobuz.com` — this review item is the gate that must confirm official access is actually in hand before the Qobuz provider (built and tested against dev-only credentials) is allowed to reach real users.
