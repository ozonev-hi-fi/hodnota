- [ ] Implement the remaining first-release providers — separate feature branch per provider, merged to `develop` one at a time; expect one shared ADR covering the common decisions across them (most of the per-provider architecture — endpoint style, catalog dedup, temp-candidate caching — was already settled in [decisions/0008](decisions/0008-youtube-search-sharepage-skeleton.md)), written when work on the first of these starts, not preemptively. That ADR is [decisions/0011](decisions/0011-spotify-provider-and-cross-provider-result-merging.md) — written when Spotify (the first of these) started, and it also covers cross-provider search-result merging, since adding a second provider without merging would show the same song once per platform.
  - [x] Spotify — implemented, but disabled since Spotify now requires an active Premium subscription on the app-owner's account to use the Web API at all; the project owner won't pay for one, so this runs dormant (config-optional, not fail-fast) until that changes — see [decisions/0011](decisions/0011-spotify-provider-and-cross-provider-result-merging.md)'s addendum.
  - [x] Qobuz — implemented (config-optional, like Spotify, since Qobuz has no self-serve developer portal). Working locally with a dev `app_id` and a dev user auth token (`catalog/search` requires both), but official credentials must still be requested from `api@qobuz.com` before this can ship to real users, see the UAT-gate ToS review item below.
  - [ ] Discogs — metadata/database + marketplace hybrid, no full playback (some samples only); not a full `IStreamingProvider`, but still produces a shareable link to the artist/release page. Interface shape decided when this item is picked up. Prioritize this one when picking the next provider: [decisions/0011](decisions/0011-spotify-provider-and-cross-provider-result-merging.md)'s YouTube search-result quality addendum documents an observed case where the same query and search window merged one album across all platforms but left a same-artist, same-shape album Qobuz-only, because YouTube's free-text video search simply never surfaced a matching item — a coverage gap in YouTube's own ranking, not something tunable from this codebase. Discogs's structured metadata is expected to be far more reliable for cross-provider matching than continuing to tune YouTube's search.
  - [ ] Tidal
  - [ ] Deezer
  - [ ] Apple Music
  - [ ] Bandcamp — selling platform with limited preview playback (1-2 plays/track); not a full `IStreamingProvider`, but still produces a shareable link. Interface shape decided when this item is picked up.
- [ ] Add observability: structured logging conventions + basic error/crash alerting — no dependency on the hosting choice below; a documentation gap surfaced by an SDLC audit, see [decisions/0010](decisions/0010-uat-production-readiness-gate.md).
- [ ] Choose and add a `LICENSE` file — before first real release/deployment, not before (repo is public now with no LICENSE, which defaults to "all rights reserved" — the safe side of the ambiguity, so no urgency). Goal is source-available but restricted against commercial use by others, not necessarily OSI-approved "open source" — plain AGPL-3.0 doesn't fit since it still permits commercial use (only requires sharing modifications). Candidates being weighed, decision still open: CC BY-NC-SA 4.0 (Creative Commons explicitly advises against using CC licenses for software — no patent handling, poor fit), PolyForm Noncommercial (built for source-available non-commercial software), Business Source License/BUSL (time-delimited commercial-use restriction that converts to a real OSS license later — used by MariaDB, Sentry, CockroachDB; may suit a scenario where investors/commercialization enter the picture later).
- [ ] Figure out hosting — must be free (or effectively free) to start.
- [ ] Backup & disaster recovery plan — depends on the hosting choice above; promotes the aspirational mention in [architecture.md](architecture.md)'s Hosting section into real, tested work, see [decisions/0010](decisions/0010-uat-production-readiness-gate.md).
- [ ] Integrate email service
- [ ] Use email service for auth confirmation flows — also a practical prerequisite for UAT itself (see below), since `RequireConfirmedAccount = true` blocks any invited tester from confirming an account without it.
- [ ] Define UAT / production-readiness gate — privacy policy published + human security review (incl. CSP, secure headers, secure cookie attributes if token storage ever moves off `localStorage`) as acceptance criteria before opening real public registration; see [decisions/0010](decisions/0010-uat-production-readiness-gate.md).
- [ ] Implement auth (Google/Facebook external login)
- [ ] Third-party streaming-API terms-of-service review (YouTube, Spotify, Qobuz, Tidal, Deezer, Apple Music, Bandcamp, Discogs) — deliberately after the UAT gate above, non-blocking for a non-commercial pre-release project, see [decisions/0010](decisions/0010-uat-production-readiness-gate.md). Spotify and Discogs added to this list after ADR 0010 was accepted — the ADR's own provider enumeration reflects the roster at the time and is left as historical record. Must cover UI-presentation rules (logo usage, attribution, linking back), not just API-usage terms — Spotify's Developer Policy is more prescriptive about presentation than YouTube's; [decisions/0011](decisions/0011-spotify-provider-and-cross-provider-result-merging.md) responded by keeping the pre-UAT UI deliberately neutral text (no logos, no brand colors, no platform-styled buttons) precisely so this review cannot force a redesign of work already shipped. Qobuz needs its own explicit check here: unlike YouTube/Spotify, it has no self-serve developer portal, and official `app_id`/`app_secret` must come from a manual request to `api@qobuz.com` — this review item is the gate that must confirm official access is actually in hand before the Qobuz provider (built and tested against dev-only credentials) is allowed to reach real users.
