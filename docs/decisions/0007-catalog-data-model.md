# 0007. Catalog data model

Status: accepted

## Context

[roadmap.md](../roadmap.md)'s next open item is "Implement the catalog data model + EF Core migrations (Postgres/SQLite)". [decisions/0003](0003-initial-architecture.md) already fixed the rough shape — a provider-agnostic catalog of `Artist`/`Album`/`Track` plus `ProviderLink`s (the reusable "Music Wikipedia" catalog from the manifesto), separate from `SharePage` — but explicitly left "detailed schema and EF Core migrations" as "implementation-time work, not fixed by this ADR." That's what this ADR settles, together with its implementation.

This is also the first schema the project designs itself. The only schema-changing feature so far, auth ([decisions/0005](0005-auth-identity.md)), got its tables from the framework (`IdentityDbContext`) — this is the first real exercise of this project's own Guid-key precedent and its dual-provider strategy (Postgres migrations for prod/dev, SQLite `EnsureCreated` for fast tests, a Testcontainers-Postgres integration-test pass for schema-changing features) against a hand-designed schema, not a supplied one.

An initial lean draft of this ADR (single-artist `Artist`/`Album`/`Track`, a compile-time `Provider` enum) was superseded before implementation after review against a more industry-standard reference design (DDEX-style: ISRC/UPC natural keys, polymorphic multi-artist credits, a dynamic platform dimension, genre tagging). This version reconciles the two: it adopts the reference design's genuinely valuable structure where it doesn't conflict with this project's own established constraints (SQLite/Postgres portability, DB-enforced referential integrity, YAGNI discipline), and explicitly rejects the parts that do conflict.

## Decision

### Entities: `Artist`, `Release`, `Track` — normalized, multi-artist-ready

All live in `Hodnota.Domain.Catalog`, keyed by `Guid` (the precedent [decisions/0005](0005-auth-identity.md) set for future catalog entities to follow).

- `Artist`: `Id`, `Name` (required), `Type` (`ArtistType`: `Person`/`Group`/`Orchestra`/`Unknown`, defaulting to `Unknown`), `ImageUrl` (nullable — a URL, not a stored image; see "Deferred" below).
- `Release`: `Id`, `Title` (required), `Type` (`ReleaseType`: `Album`/`EP`/`Single`/`Compilation`/`Live`), `ReleaseDate` (nullable `DateOnly`), `Upc` (nullable, unique when present — a natural key for future dedup matching against provider data), `CoverArtUrl` (nullable URL), `LabelId` (nullable FK to `RecordLabel`).
- `Track`: `Id`, `Title` (required), `DurationMs` (nullable `int`), `IsExplicit` (bool, default `false`), `Isrc` (nullable, unique when present — same dedup rationale as `Upc`).

**`Release` replaces "Album"** — a deliberate terminology change from [decisions/0003](0003-initial-architecture.md)/[architecture.md](../architecture.md)'s "Artist/Album/Track" language. `Release` generalizes Album/EP/Single/Compilation/Live behind one `ReleaseType`, which is what real-world provider data actually looks like (a single isn't a degenerate album, it's its own release type) and removes the need for a track to awkwardly stand alone with no parent when it isn't part of an album.

**`DurationMs` and `Confidence`-like fields stay nullable, not required**: this catalog is seeded incidentally by search results ([decisions/0003](0003-initial-architecture.md)), so a `Track` can exist as a partial stub (e.g. matched by title/ISRC from one provider) before every field is known. Requiring `DurationMs` up front, as the reference draft did, would misrepresent incomplete data as complete.

**A `Release`↔`Track` relationship is many-to-many, via `ReleaseTrack`** (`Id`, `ReleaseId`, `TrackId`, `DiscNumber` default `1`, `TrackNumber`, `TitleOverride` nullable; unique on `(ReleaseId, DiscNumber, TrackNumber)`), not a one-to-many `Track.ReleaseId` FK — the same recording (the same `Isrc`) legitimately appears on more than one release (the original album, a later compilation, a reissue), so a plain one-to-many FK on `Track` would be wrong as soon as that happens, and `Isrc`'s whole purpose is recognizing exactly this case.

**Deferred as YAGNI**, each its own future item if a real need surfaces: `Artist.Biography`/description text (a single-language `TEXT` column now would need reworking once the project's i18n approach — already an open item in [architecture.md](../architecture.md) — is settled; a URL-only `ImageUrl` has no such problem, so it stays), `Track.Lyrics` (a distinct concern from link-aggregation, with its own copyright/hosting questions nothing has asked for), locally-stored cover art/images (URLs only for v1 — storing binary images needs a hosting/blob-storage decision the roadmap hasn't reached yet).

### Multi-artist credits: `ArtistCredit`, with a DB-enforced single "main artist"

An `Artist` can be credited on a `Release` or a `Track` in more than one role — not just a single owning artist. `ArtistCredit`: `Id`, `ArtistId` (required FK), `ReleaseId`/`TrackId` (nullable FKs — exactly one set, see the CHECK-constraint pattern below), `Role` (`CreditRole`: `MainArtist`/`Featured`/`Producer`/`Composer`/`Remixer`), `CreditOrder` (int, default `1`, for display ordering among multiple credits of the same role).

The risk with a plain "one of the roles is called MainArtist" convention is that nothing stops two different artists both being credited `MainArtist` on the same release by mistake. This is enforced at the database level instead of by convention: a **partial (filtered) unique index** on `ReleaseId`, filtered to `WHERE "Role" = 'MainArtist' AND "ReleaseId" IS NOT NULL`, and the equivalent filtered on `TrackId` — guaranteeing at most one `MainArtist` credit per `Release`/`Track`, while still allowing any number of `Featured`/`Producer`/`Composer`/`Remixer` credits alongside it. Both Postgres and SQLite support filtered/partial unique indexes, so this holds on both providers.

This also answers the "band vs. compilation" question directly: a normal release has exactly one enforced `MainArtist` credit (which can be a `Group`, via `ArtistType`, just as well as a `Person`). A various-artist compilation either has zero `MainArtist` credits (the index enforces *at most* one, not *exactly* one) or, by convention, credits a real `Artist` row named "Various Artists" — an application-level choice this schema supports but doesn't build automation for (no auto-creation logic; out of scope, see Consequences).

### `Platform`: a dynamic, DB-managed catalog dimension — refining, not replacing, `IStreamingProvider`

[decisions/0003](0003-initial-architecture.md) already fixed a compile-time abstraction for *actively searching and resolving* a streaming service's API: `IStreamingProvider`, one DI-registered implementation class per service. That decision stands unchanged. What this ADR adds is a separate, DB-managed `Platform` entity (`Id`, `Name`, `Code` unique slug, `Type` — `PlatformType`: `StreamingService`/`DigitalStore`/`PhysicalStore`/`Aggregator`/`Database`, `WebsiteUrl`/`IconUrl` nullable) representing the broader catalog-side dimension a link can point to.

These are deliberately two different concerns: `IStreamingProvider` is "how do we talk to a service's API to search and resolve," a code abstraction that only exists for services this project has built integration code for. `Platform` is "which external service does this link point to," a data dimension — which lets the catalog carry a `ProviderLink` to a service with no automated search integration at all (e.g. Discogs, Beatport as pure manually-added links) without a code deploy, and lets links be grouped/categorized by `Platform.Type` for future UI sections ("Stream" / "Buy Digital" / "Buy Physical") independent of which services are actively integrated. Each `IStreamingProvider` implementation creates `ProviderLink`s tagged with the matching seeded `Platform.Code`.

Removing a `Platform` isn't safe: `ProviderLink.PlatformId` is `DeleteBehavior.Restrict` specifically so a `Platform` with existing links can't be deleted out from under them, but that also means dropping a discontinued platform from the `HasData` seed list would generate a `DeleteData` that fails outright against any database holding real links to it. `Platform.IsActive` (bool, default `true`) is the intended way to retire a platform instead: the application stops creating new `ProviderLink`s for an inactive platform, existing links and their history are untouched, and no delete — soft or hard — is ever required. Nothing enforces `IsActive` at the database level (a CHECK that "new links must target an active platform" would need to inspect a different table, which plain CHECK constraints can't do); that responsibility belongs to whatever future code creates `ProviderLink`s, not the schema.

`Platform` is seeded via `HasData` with hardcoded, deterministic `Guid` literals (required by `HasData`) for the services already named in [architecture.md](../architecture.md)'s supported-services list: YouTube, YouTube Music, Qobuz, Tidal, Deezer, Apple Music (all `Type = StreamingService`), and Bandcamp (`Type = DigitalStore`, matching architecture.md's existing "Purchase Platforms" split from the streaming list).

### `ProviderLink`'s association to `Artist`/`Release`/`Track`, and the general "partial index per target type" pattern

`ProviderLink`: `Id`, `ArtistId`/`ReleaseId`/`TrackId` (nullable FKs), `PlatformId` (required FK to `Platform`), `ExternalId`/`ExternalUrl` (both required), `Confidence` (nullable `double`), `LastVerifiedUtc` (nullable `DateTimeOffset`).

A database CHECK constraint (portable `CASE`-based boolean-sum form — `(CASE WHEN "ArtistId" IS NOT NULL THEN 1 ELSE 0 END) + ... = 1`, not Postgres-only cast syntax, so it runs unchanged on both Npgsql and SQLite) enforces that exactly one of the three FKs is set. Rejected, as in the original draft of this ADR: a shared `CatalogEntry` base/TPT-style table (real mapping ceremony for zero query benefit — nothing needs a polymorphic "all catalog entries" query yet), and three separate per-type join tables (triples the entity/config/migration surface for no gain over one table plus a constraint). Also rejected, from the reference draft: a loose `entity_type`/`entity_id` string-and-Guid pair with no real foreign key — it sacrifices DB-enforced referential integrity for a flexibility this closed, three-member set of target types doesn't need.

**Uniqueness** (no duplicate link to the same platform for the same catalog entity) needs **three separate partial unique indexes**, one per target column — `(PlatformId, ArtistId) WHERE ArtistId IS NOT NULL`, and the `ReleaseId`/`TrackId` analogues — **not one composite unique index** across all three nullable columns. Standard SQL NULL semantics mean a composite unique constraint treats two rows as non-duplicate as soon as any column differs by being NULL in both, even when the same target and platform repeat — a naive composite index would silently fail to catch a real duplicate. This is a general, reusable pattern for every polymorphic nullable-FK table in this schema: it also applies to `ArtistCredit`'s `MainArtist` uniqueness (above) and to `EntityGenre`, below.

### `Genre`/`EntityGenre`, and `RecordLabel`

`Genre` (`Id`, `Name` unique, `Slug` unique) and `EntityGenre` — a `Genre` tag applied to an `Artist`, `Release`, or `Track` (`Id`, `GenreId` required FK, `ArtistId`/`ReleaseId`/`TrackId` nullable FKs) — use the same "exactly one target" CHECK constraint and the same three-partial-unique-indexes-per-target-type pattern as `ProviderLink`.

`RecordLabel` (`Id`, `Name`) is a plain lookup entity; `Release.LabelId` is a nullable FK with `DeleteBehavior.SetNull` (losing a label shouldn't cascade-delete the release itself).

Both were reference-draft additions with no current consumer (no genre-driven search/filter UI, no label-ingestion logic exists yet), but are included now rather than deferred: unlike the schema-shape decisions above, `Genre`/`RecordLabel` are purely additive lookup tables with no entanglement in the core `Artist`/`Release`/`Track`/`ArtistCredit` relationships — adding them later would cost nothing extra, so there's no YAGNI penalty either way, and having them now avoids a second small migration.

Deferred, from the reference draft: JSONB-style flexible `metadata` columns on any table — SQLite has no `jsonb` equivalent (would need a portable JSON-string workaround), and nothing in the codebase needs unstructured extra fields yet. Columns get added when an actual consumer needs them, per this project's established convention.

### Audit timestamps via a shared interface and a `SaveChanges` interceptor

`IHasTimestamps` (`CreatedAtUtc`, `UpdatedAtUtc`, both `DateTimeOffset`) is implemented by every primary/lookup entity — `Artist`, `Release`, `Track`, `Platform`, `Genre`, `RecordLabel`, `ProviderLink` — but deliberately not by the pure join tables (`ReleaseTrack`, `ArtistCredit`, `EntityGenre`), which have no independent lifecycle worth auditing. A `TimestampsInterceptor : SaveChangesInterceptor` in `Hodnota.Infrastructure`, using an injected `TimeProvider` (not `DateTimeOffset.UtcNow` directly, for testability — a new pattern for this codebase), sets both timestamps on insert and just `UpdatedAtUtc` on update. `Platform`'s seeded rows are the one exception: `HasData` requires literal values, so their timestamps are a fixed constant, not interceptor-derived — `HasData` rows go through migration `InsertData`, never `SaveChangesAsync`.

### Catalog `DbSet`s join the existing `ApplicationDbContext`, not a new dedicated `CatalogDbContext`

Unchanged from the original draft of this ADR: this is the project's first `OnModelCreating` override (`base.OnModelCreating(builder)` first for Identity, then `builder.ApplyConfigurationsFromAssembly(...)` picking up new `IEntityTypeConfiguration<T>` classes under `Hodnota.Infrastructure/Catalog/`). Matches [decisions/0005](0005-auth-identity.md)'s "single Postgres-only migration set" precedent; avoids bounded-context ceremony (two migrations-history tables, two design-time factories) that buys nothing for a solo project with no scaling pressure yet.

One consequence revisited mid-implementation: the single migration history was originally generated into `Hodnota.Infrastructure/Identity/Migrations/`, matching where `ApplicationDbContext` happens to live since [decisions/0005](0005-auth-identity.md) put it there for auth. Once this ADR's migration made that folder hold the whole app's schema, not just Identity's, the name stopped fitting — so migrations were relocated to `Hodnota.Infrastructure/Migrations/` at the project root instead, a plain folder/namespace move with no behavior change. Since nothing has ever been deployed past a local dev machine, the two migrations that existed at that point (`InitialCreateIdentity`, `AddCatalogSchema`) were squashed into a single fresh `InitialCreate` in the new location rather than carried forward — there is no production/UAT history this would break, and keeping two migrations whose split no longer means anything (both belonged to the same never-shipped starting point) wasn't worth preserving. A project with a real deployed history would instead move the files in place and keep the sequence, since a squash there would break `dotnet ef database update` on any environment already past the old migrations.

### URL columns are `Uri`, not `string`; every `DateTimeOffset` is normalized to UTC

`ImageUrl`, `CoverArtUrl`, `WebsiteUrl`, `IconUrl`, and `ExternalUrl` are typed `Uri`/`Uri?`, not `string`/`string?` — a malformed value fails at construction time instead of being silently persisted, and the type communicates "this holds a well-formed absolute URL" without a comment. A single `UriValueConverter : ValueConverter<Uri, string>`, registered once in `ApplicationDbContext.ConfigureConventions` (`configurationBuilder.Properties<Uri>().HaveConversion<UriValueConverter>()`), applies to every `Uri`/`Uri?` property in the model — the underlying column stays the same `text`/`character varying` type on both providers, so this needed no new migration.

The same `ConfigureConventions` override applies a `UtcDateTimeOffsetConverter` (`.ToUniversalTime()` on write) to every `DateTimeOffset` property in the model, not just the ones this ADR added. `TimestampsInterceptor` already only ever writes `TimeProvider.GetUtcNow()`, but `LastVerifiedUtc` is a plain settable property future code could otherwise populate with a non-UTC value by mistake (e.g. `DateTimeOffset.Now`); a model-wide converter closes that gap for every current and future `DateTimeOffset` column — including Identity's own `LockoutEnd` — rather than relying on every call site remembering the convention. Applying it as a `ConfigureConventions` model-wide rule instead of a per-property `.HasConversion(...)` call means a future `DateTimeOffset` property gets the same guarantee automatically, with nothing to remember.

### Self-documentation: `[Description]`, not comments, for non-obvious property meaning

Properties whose meaning isn't obvious from their name alone (`Upc`, `Isrc`, `Platform.Code`, `ProviderLink.ExternalId`/`Confidence`/`LastVerifiedUtc`, `Genre.Slug`, `ArtistCredit.CreditOrder`, `ReleaseTrack.TitleOverride`) carry a `[Description("...")]` attribute (`System.ComponentModel`, part of the base class library — no new dependency) instead of a `//` comment. This keeps the explanation attached to the member for any future reflection-based use (a self-documenting schema/admin view, generated API docs) rather than living only in a source file a reader happens to open.

This is separate from, and doesn't replace, this repo's now-explicit rule (see [CLAUDE.md](../../CLAUDE.md)) against comments that restate a decision already covered by its ADR: a `[Description]` documents what a field *is*, not why it's shaped the way it is — the entity/configuration files in this feature accordingly carry very few inline comments, since the "why" lives here instead.

### `SharePage` and repository interfaces stay out of scope

Unchanged from the original draft: `SharePage` is deferred to its own ADR when "Implement a first streaming provider end-to-end as a walking skeleton" actually starts — its shape isn't forced by any concrete requirement yet. `Hodnota.Application` stays empty of catalog repository interfaces until that same walking-skeleton item defines a real query/search use case; guessing the shape now, against zero callers, risks designing the wrong interface before the actual access pattern (likely intertwined with `IStreamingProvider` search, not plain CRUD) is known.

## Consequences

- Deliberately deferred, each its own future roadmap/ADR item: `SharePage`, repository interfaces, `Artist.Biography`/localized description text, `Track.Lyrics`, JSONB/flexible metadata columns, auto-creation logic for a "Various Artists" artist row, local/blob image storage, DB- or service-level enforcement that new `ProviderLink`s target only an active `Platform`.
- Rejected from the reference draft, beyond what's noted inline above: a redundant `platform` enum column alongside a `platform_id` FK (kept only the FK).
- `Release` replaces "Album" as this project's terminology going forward — [architecture.md](../architecture.md)'s Data Model section is updated to match once implemented.
- Migrations moved from `Hodnota.Infrastructure/Identity/Migrations/` to `Hodnota.Infrastructure/Migrations/`, squashed to a single `InitialCreate` — see the "Catalog `DbSet`s join..." section above. `README.md`'s `dotnet ef migrations add` example is updated to the new `-o Migrations` path.
- Establishes conventions future entities/tests should follow: the `Hodnota.Infrastructure/Catalog/` `IEntityTypeConfiguration<T>` pattern; `TimeProvider`-based timestamping via a `SaveChangesInterceptor` rather than direct `DateTimeOffset.UtcNow` calls; `Uri` (not `string`) for URL columns and a model-wide UTC-normalizing converter for every `DateTimeOffset`, both via `ConfigureConventions`; and `[Description]` attributes, not comments, for non-obvious property meaning.
- [architecture.md](../architecture.md)'s Data Model and Open Questions sections and [roadmap.md](../roadmap.md)'s catalog checkbox are updated once this schema is actually implemented and tested (migrations committed), not by this document alone.
- New test coverage: a SQLite `EnsureCreated`-based fast-test file covering every entity, every CHECK constraint, and every partial unique index (including the "multiple non-`MainArtist` credits still allowed" and "multiple NULLs still allowed" sanity checks), plus a Postgres integration-test file re-verifying the constraints against a real database, per this project's existing schema-change testing rule.
