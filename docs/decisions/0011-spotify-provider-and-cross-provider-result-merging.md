# 0011. Spotify provider and cross-provider search-result merging

Status: accepted

## Context

[roadmap.md](../roadmap.md)'s next open item is "Implement the remaining first-release providers", starting with Spotify, with an explicit note that the shared cross-provider ADR is written "when work on the first of these starts, not preemptively." This is that ADR.

The requested feature turned out to be bigger than "add a second `IStreamingProvider`." The underlying user story: a user types a half-remembered, possibly-misspelled query ("Metallica Nothing"), presses search, and expects a short list of candidates to pick from — not caring which platform a result came from, and specifically **not** expecting to see the same song listed once per platform. Today's `CatalogSearchService` ([decisions/0008](0008-youtube-search-sharepage-skeleton.md)) simply concatenates every registered provider's results. That's invisible with one provider. Adding Spotify alongside YouTube without merging would return the same song twice for nearly every query — exactly the outcome the user story rules out.

So this ADR covers two things together, because the second cannot be honestly designed or tested without the first: the Spotify provider itself, and cross-provider result merging. It also revisits two things ADR 0008 explicitly deferred: "matching a new provider's result against an existing catalog entity that has no YouTube link at all" (its dedup section), and per-provider failure isolation (today one provider throwing fails the entire search — tolerable with one provider, not with several).

Typo tolerance is not built by this project — it's delegated entirely to each platform's own search, which is already good at it. hodnota's job is only to avoid presenting the same result twice.

## Decision

### Spotify client: raw `HttpClient`, not a community SDK

Spotify publishes no official first-party .NET SDK. Per [decisions/0008](0008-youtube-search-sharepage-skeleton.md)'s rule — "an official free SDK when the vendor provides one, a raw `HttpClient` otherwise" — this selects the raw-`HttpClient` branch, via `IHttpClientFactory`. This is the first use of `IHttpClientFactory` in the codebase; it needs no new package, since `Microsoft.Extensions.Http` ships inside the `Microsoft.AspNetCore.App` framework reference `Hodnota.Infrastructure.csproj` already carries.

Authentication is the Client Credentials flow (`POST https://accounts.spotify.com/api/token`, HTTP Basic with client id/secret, `grant_type=client_credentials`), appropriate because hodnota never acts on behalf of a Spotify user — it only searches Spotify's public catalog. The token (`expires_in` = 3600s, no refresh token issued — the same grant is simply re-run) is cached in a singleton and refreshed shortly before expiry.

Search is one call covering both types: `GET /v1/search?q={query}&type=track,album&limit=5`, optionally `&market={code}`. One round trip, one rate-limit unit, for both a song and an album candidate list. Rate limiting is a rolling 30-second window with no published number; on a `429`, the client does not sleep-and-retry — it logs and throws, letting failure isolation (below) drop Spotify for that one query while YouTube still answers. Blocking an interactive search is worse than a shorter result list.

`market` is **omitted** by default, exposed as an optional `Spotify:Market` config key. Omitting it returns the widest possible catalog with no country bias; hodnota produces a link, not playback, so a track unavailable in one viewer's country still resolves to a real Spotify page.

**Rejected alternative: `SpotifyAPI-NET`** (the well-known community wrapper). It is community-maintained, so it fails ADR 0008's "official" bar, and the surface actually needed — one token grant, one search call — is small enough to hand-write without taking on a whole dependency and its transitive footprint in the SBOM/dependency-review gate ([decisions/0008](0008-youtube-search-sharepage-skeleton.md)'s CI scanning section).

`album_type` (`album` | `single` | `compilation`) maps onto the existing `Hodnota.Domain.Catalog.ReleaseType` enum (`Album`/`EP`/`Single`/`Compilation`/`Live`) as `album`→`Album`, `single`→`Single`, `compilation`→`Compilation`, anything else→`Album`. `EP` and `Live` stay unreachable from Spotify search — Spotify itself classifies EPs as `single`, and guessing from track count would be wrong often enough to be worse than the `Single` default. `StreamingSearchResult` gains an optional `ReleaseType?` so this signal isn't silently discarded the way ADR 0008 accepted for YouTube (whose playlists carry no such signal at all).

ISRC (`external_ids.isrc`, present on Spotify track search results) and UPC (absent from Spotify's album search results, only available via a follow-up `GET /v1/albums/{id}`) are **not used for matching in this pass**. YouTube exposes neither, so there is nothing on the other side to compare against yet. This becomes a real two-tier strategy (exact ISRC match, normalized-key fallback) once a second ISRC-bearing provider — Deezer, Tidal, or Qobuz all expose it — lands.

### Provider identity: `ProviderCode` on the interface; trust ranking in one array

`IStreamingProvider` ([decisions/0008](0008-youtube-search-sharepage-skeleton.md)) had no notion of provider identity — nothing needed it with only one implementation. Merging needs two things this doesn't provide: which provider produced a result, and a relative trust ranking between providers (see the merge model below).

```csharp
public interface IStreamingProvider
{
    string ProviderCode { get; }
    Task<IReadOnlyList<StreamingSearchResult>> SearchAsync(string query, CancellationToken cancellationToken);
}
```

Identity (`ProviderCode`) is a property on the interface because only the provider itself genuinely knows what it is. Trust ranking is **not** a second property on the same interface — it lives in one small `ProviderTrustOrder` array in `Hodnota.Application.Catalog`, ordered highest-trust first. The reasoning: identity is a fact about one class; relative trust is a statement about the whole set, and a set-level decision belongs in exactly one place. Scattering an `int TrustRank` across every provider class means reordering providers is an N-file diff and needs gap management (10/20/30…) to insert one in the middle; a single array makes "what is the trust order?" answerable by one grep, and reordering a one-line change. Because the array keys on provider-code strings rather than a shared base type, it already accommodates the roadmap's odd future entries (Bandcamp, Discogs) that won't be full `IStreamingProvider`s.

**Rejected alternatives:** DI registration order (`IEnumerable<T>` does preserve it, but it's implicit, unassertable in a test, and `CatalogApiFactory`'s `RemoveAll<IStreamingProvider>()` + re-add already makes test registration order an accident, not a guarantee); a config-driven priority list (this is a product/editorial decision, not a deployment knob, and the project has no `IOptions` pattern to hang it on anyway).

Spotify ranks above YouTube: Spotify's `name`/`artists`/`images` are clean structured metadata, while YouTube's video title is free text and its `ChannelTitle` is frequently a label, VEVO channel, or aggregator rather than the actual artist.

`ProviderLinkCandidate.PlatformCode`'s existing string reference from `Hodnota.Application` into `Hodnota.Infrastructure.Catalog.PlatformCodes` is a known pre-existing smell, unrelated to this feature. It is not fixed here — doing so would touch roughly nine files unrelated to providers or merging, in a branch that is already large. This feature adds exactly one new value to that existing set (`spotify`) without deepening the coupling; a future cleanup can relocate `PlatformCodes` to `Hodnota.Domain.Catalog`, next to `Platform` itself.

### Cross-provider merging: a "spine" model with normalized-key matching

**The model.** Providers are consulted in trust order. The highest-trust provider that actually returns results becomes the spine: its results form the base rows, in its own relevance order, and its metadata (name, artist, image) is what the merged row displays. A lower-trust provider's result attaches to a spine row when it matches; a lower-trust result that matches nothing is appended after the spine rows, in trust order. This is not a separate "pick the spine" step — it emerges from processing providers in order with a first-writer-wins index: whichever result claims a match key first owns the row, and everything after it that claims the same key only contributes its links. If the top-trust provider returns nothing (or fails — see below), the next provider's first result becomes the spine automatically, with no special-cased fallback logic.

**The match key deliberately does not require exact string equality**, because the same recording routinely has almost nothing else in common across providers: `Nothing Else Matters` (Spotify) versus `Metallica - Nothing Else Matters (Official Music Video)` (YouTube), artist `Metallica` versus channel `MetallicaVEVO`. Matching normalizes both the artist and the title — lowercasing, Unicode diacritic folding, stripping a fixed list of noise terms (`(Official Music Video)`, `[Remastered 2021]`, `- Topic` channel suffixes, `VEVO` suffixes, `feat. X` segments) — and then strips the normalized artist from the normalized title as a prefix or suffix, since that's exactly the difference between a YouTube video title and a Spotify track name. The result type (`Track` vs `Release`) is the first component of the key, so a song can never merge with an album of the same name by the same artist. This is **not** a general fuzzy-similarity score (e.g. Jaro-Winkler) — a single tunable threshold was rejected because no one number correctly separates "same song, different noise" from "different song, similar title" (e.g. `Nothing Else Matters` vs `Nothing Else Matters (Live)`, which must stay separate).

**The stated bias, and it governs every ambiguous call in the normalizer: prefer a missed merge over a false merge.** A missed merge costs the user one extra line to scan. A false merge sends a friend to the wrong recording via a share page, silently, and persists the wrong link in the catalog. Concretely, this is why `live`, `remix`, `acoustic`, `demo`, `cover`, and similar qualifiers are deliberately **not** in the noise-stripping list even though they'd increase the merge rate — stripping them would merge genuinely different recordings.

Links from a matching lower-trust result are unioned onto the spine row, deduplicated **by platform code**, first-occurrence-wins — not by `(platform, externalId)`, since a spine provider commonly returns near-duplicate results itself (e.g. Spotify's own remaster and original both matching one row), and deduplicating only by external id would leave two links for the same platform pointing at different URLs on one row. Because link order comes from trust order, and `EfCatalogRepository` (below) assigns `SharePageLink.DisplayOrder` from that same order, **trust order becomes the visible link order on every share page** — a deliberate, if easy-to-forget, coupling.

**Failure and "no results" are indistinguishable to the merge step by design.** Per-provider failure isolation (next section) converts a thrown exception into an empty result list before the merge algorithm ever sees it, so the merge logic itself needs no knowledge of failures — it already handles "this provider produced nothing" as its normal fallback-to-next-provider case.

**Known limitation, accepted rather than solved here:** a false merge is still possible when two providers' noise-stripped keys coincide despite being genuinely different content — e.g. a YouTube upload titled exactly `Metallica - Nothing Else Matters` on a channel named `Metallica` that is actually a fan-made live recording. Nothing short of duration or ISRC comparison catches this, and neither is available cross-provider yet (see the ISRC note above). This is recorded as a known, accepted gap, not silently ignored.

### Per-provider failure isolation

`CatalogSearchService.SearchAsync` still calls every provider concurrently via `Task.WhenAll` — concurrency was never the problem. The problem was that `Task.WhenAll` propagates the first exception and fails the entire search, which was tolerable with exactly one provider and is not with several: YouTube's own free-tier quota (10,000 units/day, ~100 searches — [decisions/0008](0008-youtube-search-sharepage-skeleton.md)) makes single-provider outages a routine event, not a rare one.

Each provider call is now wrapped so it cannot throw past its own boundary: a caught exception becomes an empty result list plus one `LogWarning` (provider code as a structured parameter). Cancellation requested by the caller is re-thrown, not swallowed, so a user navigating away doesn't get logged as a wall of provider failures. **Only when every registered provider fails** does the search still throw `StreamingProviderException`, surfacing the existing controller-level `400 Bad Request` — a genuinely-down search is still reported as such; a partially-degraded one is not. No user-visible warning exists for a partial failure — decision, not oversight: the user asked not to see failures at all, only for the results that are available.

This adds `Microsoft.Extensions.Logging.Abstractions` to `Hodnota.Application` — a dependency-free Microsoft abstractions package that commits to nothing about how logging is eventually configured. Only one `LogWarning` per failed provider is added in this pass; structured logging conventions, correlation ids, and timing/metrics logging are left to the roadmap's still-open observability item, deliberately.

### Search-result display: neutral text, platform links shown per row

Each search-result row shows the platform links it actually carries as plain text labels — e.g. `Spotify · YouTube · YouTube Music` — so what the row promises matches exactly what its resulting share page will contain (a YouTube-only row genuinely has both a `youtube` and a `youtube-music` link, so both are shown). `SearchCandidateResponse` gains an ordered `Platforms` list for this, derived from the merged result's `Links`.

**No platform logos, brand colors, or platform-styled buttons are used anywhere in this feature — search rows or the share page — until the UAT gate.** This is a direct consequence of the still-open, UAT-gate-deferred "third-party streaming-API terms-of-service review" ([decisions/0010](0010-uat-production-readiness-gate.md)): Spotify's Developer Policy is more prescriptive than YouTube's specifically about UI presentation (logo usage rules, required attribution, linking-back requirements), and a text-only presentation cannot be made non-compliant by that future review — there is nothing to redesign.

### Addendum: Spotify access is blocked without a Premium subscription; the provider is optional, not fail-fast

Discovered after the above was implemented and merged into this branch, not anticipated at design time.

Since February 2026, Spotify requires the Spotify account that owns a Web API app to have an **active Premium subscription**, just to use the app in Development Mode — the mode every app starts in, and the only mode this project's Client Credentials flow (see above) has ever run in. Without it, every Web API call, including `/v1/search`, returns `403`. Extended Quota Mode would remove this requirement, but has been closed to projects like this one since May 2025: it's granted only to a registered business with 250,000+ monthly active users. Neither path is available to hodnota, and the project owner will not pay for Premium to work around it.

This is a runtime/operational fact about the vendor, not a flaw in the design above — the client, the token caching, the merge model, and the trust-order mechanism are all unaffected and remain the pattern future providers follow. What changes is a single assumption made in "Provider identity" and mirrored in `Hodnota.Infrastructure.DependencyInjection`: that a configured provider's credentials being present means it will actually work. For Spotify, valid credentials do not imply working access, and no amount of local configuration fixes that.

**Decision:** Spotify becomes the codebase's first *optional* provider. `Spotify:ClientId`/`Spotify:ClientSecret` being unset is treated as "Spotify is not available," not as a startup misconfiguration — `DependencyInjection.AddCatalog` skips registering `SpotifyCredentials`, its two named `HttpClient`s, `SpotifyAccessTokenProvider`, `SpotifyApiClient`, and `IStreamingProvider → SpotifyStreamingProvider` entirely when either is missing, and `Program.cs` no longer force-resolves `SpotifyCredentials` at startup. `CatalogSearchService` needs no change for this — it already iterates whatever `IStreamingProvider`s are registered. YouTube's own config keeps failing fast: unlike Spotify, a missing/invalid YouTube API key is fixable locally, so treating it as a hard startup error is still correct there.

**Consequence:** running hodnota today, Spotify search results simply don't appear — the app behaves as if Spotify were never added, with no error, no log noise beyond a one-time absence at startup. This is expected, not degraded operation, and should not be "fixed" by re-adding a fail-fast check unless Spotify's policy changes or a Premium-owning account's credentials are supplied.

### Addendum: Qobuz provider added; `StreamingSearchResult` gains `Isrc`/`Upc`, matching itself unchanged

Qobuz is the third provider (`Hodnota.Infrastructure.Providers.Qobuz`), following the same raw-`HttpClient` path as Spotify — Qobuz has no official .NET SDK either. Its access situation differs from both existing providers: there is no self-serve developer portal at all, and local/dev credentials are obtained outside any officially guaranteed channel (see `CLAUDE.local.md`, kept private given the sensitivity of that reasoning). Search needs both an `app_id` and a `user_auth_token` — no `app_secret`, no OAuth-style token refresh, but `catalog/search` rejects `app_id` alone with a 401 — which still makes `QobuzApiClient` simpler than `SpotifyApiClient`: two static headers, one call, no token-provider class. Qobuz follows Spotify's config-optional registration pattern in `DependencyInjection.AddCatalog`, for the same reason: an arbitrary contributor cannot self-serve their way to a working `app_id`/`user_auth_token` pair, so its absence means "not available," not "misconfigured."

Qobuz ranks highest in `ProviderTrustOrder` — its search results carry clean structured metadata plus ISRC (tracks) and UPC (albums) directly, exceeding what Spotify's own search response exposes for UPC.

This is also the "second ISRC-bearing provider" this ADR's own Consequences section named as the trigger for a future two-tier matching upgrade. That upgrade is **not** implemented in this pass — deliberately. `StreamingSearchResult` gains nullable `Isrc`/`Upc` fields, populated by Qobuz (both) and Spotify (`Isrc` only, from `external_ids.isrc`, already present in Spotify's response but unused until now — Spotify's album search still carries no UPC, so that stays null there), but `SearchResultKey`/`SearchResultMerger` are untouched: merging is still normalized-key-only. The data now flows through the model ready for the exact-match upgrade; the algorithm change itself remains a distinct, deferred piece of work.

### Addendum: YouTube search-result quality — wider window, and a relevance filter for zero-overlap results

Discovered through manual testing after the above shipped: searching "aurora different kind" returned the right Qobuz albums, but the matching YouTube Music album playlists (which do exist) never appeared, so no merge happened and the share page for that album carried only the Qobuz link. Separately, the YouTube-only rows in that same result list included at least one item (a Russian-language video whose channel name happens to look like "Aurora") with no real connection to the query at all.

Two independent, narrow fixes, both scoped to `YouTubeStreamingProvider` only:

**Wider search window.** `SearchAsync`'s `request.MaxResults` goes from 10 to 50 — the YouTube Data API's own maximum for `search.list`. This call already costs a flat 100 quota units regardless of `MaxResults` ([decisions/0008](0008-youtube-search-sharepage-skeleton.md)'s quota note), so this is free in quota terms. It only improves the odds that the real matching item (e.g. an official album playlist) is inside the page YouTube returns — it does not guarantee it, and a wider window also means the raw list has room for more irrelevant items before filtering.

**A relevance filter, not a quality filter.** `SearchResultRelevanceFilter.IsRelevant(query, result)` (new, `Hodnota.Application.Catalog`, public because a future noisy free-text provider can reuse it) drops a result only when it shares **zero** words (3+ letters, to skip short filler words) with the query, checked against the result's normalized name and artist. This is deliberately the weakest filter that still catches the observed case: it removes a result with no textual relation to the query at all (different script, unrelated content), but it does **not** attempt to judge a result's authority or official-ness — an unofficial fan upload whose title genuinely contains the query's words is kept, same as before. Extending the ADR 0011 bias ("prefer a missed merge over a false merge") to display: matching just one shared word is enough to keep a result, so the false-negative risk (wrongly hiding something real) stays as low as the false-positive risk (a query too short to judge, e.g. "U2", disables the filter entirely rather than dropping everything).

Wired into `YouTubeStreamingProvider.SearchAsync` only, after the existing `ToSearchResult` mapping — not into `CatalogSearchService` for every provider, and not into Qobuz or Spotify, since both already do structured, fielded search server-side and applying a free-text word-overlap filter on top of that risks dropping a legitimately fuzzy match neither provider's own text search would have surfaced as noise in the first place.

**Known limitation, confirmed rather than just anticipated:** a wider window only reduces, not removes, the chance that YouTube's top 50 mixed video/playlist results for a given query simply don't include the canonical item — this is not a hypothetical. Re-testing "aurora different kind" after the widening: "A Different Kind Of Human – Step 2" now merges across all three platforms, but "Infections Of A Different Kind – Step 1" — same artist, same query, same 50-item window — still only finds Qobuz. YouTube's own free-text search simply didn't surface an "Infections..." playlist by AURORA at all, official or not, anywhere in the 50 items it returned. Chasing this further by tuning window size or filter wording is not expected to be worth it: the two albums got different outcomes from the identical query and window, which points at YouTube's own search ranking being the limiting factor, not a parameter this codebase controls. [roadmap.md](../roadmap.md)'s Discogs item is the intended longer-term answer — structured metadata instead of free-text video search — not further tuning here.

### Addendum: a cap on displayed results, applied after merging

The widened YouTube window (previous addendum) also means a query can return a long tail of individually-legitimate-but-unhelpful YouTube rows — for "aurora different kind," around 50 of them, each sharing real words with the query so the relevance filter correctly keeps every one. This is the "post-merge result cap" this ADR's own Consequences section had named as deliberately deferred; manual testing showed the cost of deferring it (a result list several screens long) outweighs waiting for a cleaner motivating case.

`CatalogSearchService.SearchAsync` now takes only the first `MaxMergedResults` (20) rows after `SearchResultMerger.Merge`, before storing them in the candidate cache — uncapped rows are never cached, not just hidden, so there's nothing to resolve later even if a client somehow requested one. Trust order already puts every spine (Qobuz) row, merged or not, ahead of any leftover unmatched YouTube row (`SearchResultMerger`'s own ordering, unchanged), so the cap trims exactly the long unmerged tail first — it does not risk cutting off a `Qobuz` row to make room for a `YouTube` one.

20 is a starting guess, not a measured number — easy to change in one place if it turns out to be too tight or too loose in practice.

## Consequences

- Establishes `Hodnota.Infrastructure.Providers.Spotify` as the codebase's first hand-rolled `HttpClient`-based provider and its first `IHttpClientFactory` usage, per [decisions/0003](0003-initial-architecture.md)'s original provider-abstraction sketch.
- `IStreamingProvider` gains `ProviderCode`; every existing and future implementation must supply one. `ProviderTrustOrder` becomes the single place that answers "what order do providers get trusted in" — future provider work reads and edits this file, not scattered per-provider constants.
- Introduces genuine cross-provider search-result merging for the first time; catalog dedup at *resolve* time (exact `ProviderLink(PlatformId, ExternalId)` match, [decisions/0008](0008-youtube-search-sharepage-skeleton.md)) is unchanged and remains a distinct mechanism from normalized-key merging at *search* time — the two operate at different stages and must not be confused when reading the code.
- Fixes a latent bug in `EfCatalogRepository`: resolving a candidate whose result already matches an existing catalog entity previously returned only that entity's already-persisted links, silently discarding any new platform links the candidate also carried. Harmless with one provider (YouTube's two links are always created together), but became the routine case once a merged candidate carries both a new Spotify link and a pre-existing YouTube link. Fixed to insert any not-yet-persisted candidate link onto the resolved entity, while still skipping (not inserting) a link whose `(platform, externalId)` already belongs to a *different* entity, preserving the existing non-crashing behavior for that edge case.
- `CatalogSearchService` no longer fails an entire search because one provider is unavailable; only a total failure across every registered provider does. This is a behavior change from [decisions/0008](0008-youtube-search-sharepage-skeleton.md), justified by moving from one provider to several.
- Adds `SearchResultRelevanceFilter` and widens YouTube's search window (see the addendum above) after manual testing surfaced both an under-merged album (YouTube's top-10 window didn't contain the matching playlist) and a zero-relation result reaching the list (a different-script video with no real connection to the query). Re-testing after the widening confirmed the underlying coverage gap is real, not just theoretical (see that addendum's "Known limitation") — [roadmap.md](../roadmap.md)'s Discogs item is the named direction for actually closing it, not further YouTube-side tuning.
- Implements the post-merge result cap this ADR previously deferred (see the addendum above) — `CatalogSearchService` now caps the merged list at 20 rows before caching, so a wide YouTube window improves merge odds without also lengthening the list a user has to scan.
- Deliberately deferred, each a named future item: ISRC/UPC-based matching — the *data* is no longer deferred (see the Qobuz addendum below, `StreamingSearchResult.Isrc`/`Upc` are now populated), but the matching *algorithm* upgrade itself still is — relocating `PlatformCodes` out of `Hodnota.Infrastructure`, and structured logging conventions generally (roadmap's observability item). Spotify's extended-quota request is not deferred but dropped — see the addendum above; it is not obtainable by a project at this scale under Spotify's post-May-2025 criteria.
- Spotify and Qobuz are both registered conditionally, unlike YouTube — see the addenda above. Both are providers whose absence is a normal, expected runtime state rather than a startup misconfiguration.
- [roadmap.md](../roadmap.md)'s Spotify and Qobuz sub-items are both checked off, and its "third-party streaming-API terms-of-service review" item is expanded to note that Spotify's policy covers UI presentation specifically, and that this feature's neutral-text UI is a deliberate response to that, not an oversight to fix later.
- [architecture.md](../architecture.md)'s streaming-provider integration section is updated to describe Spotify and Qobuz alongside YouTube, the trust-order/merge model, and per-provider failure isolation.
