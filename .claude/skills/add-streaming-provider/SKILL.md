---

hodnota has five `IStreamingProvider` implementations today — YouTube (`Hodnota.Infrastructure.Providers.YouTube`, official SDK) and Spotify, Qobuz, Discogs, and Tidal (`Hodnota.Infrastructure.Providers.*`, raw `HttpClient`) — and [docs/roadmap.md](../../../docs/roadmap.md) lists the remaining planned ones (Deezer, Apple Music, Bandcamp). Adding Spotify repeated most of what YouTube had already established; this skill captures that repeatable part (provider codes, trust order, DI registration, config keys, appsettings, tests, docs) so each new provider only has to supply the genuinely new part (the vendor's own client, DTOs, and mapping logic). [decisions/0008](../../../docs/decisions/0008-youtube-search-sharepage-skeleton.md) and [decisions/0011](../../../docs/decisions/0011-spotify-provider-and-cross-provider-result-merging.md) already settled *why* the architecture looks like this — this skill doesn't re-derive that reasoning, it links to it and tells you which file to touch and in what order.

Per [docs/roadmap.md](../../../docs/roadmap.md)'s "Implement the remaining first-release providers" item, each provider is its own branch off `develop`, merged one at a time — don't bundle two providers into one branch. Name it `feature/NNNN-x-provider` after its ADR (see row 14 below — most providers get one), `feature/x-provider` only if it has none. Check the current branch against `CLAUDE.md`'s branching rule before starting.

## Prerequisites

- Read [decisions/0008](../../../docs/decisions/0008-youtube-search-sharepage-skeleton.md) in full (`IStreamingProvider` shape, SDK-vs-`HttpClient` rule) and [decisions/0011](../../../docs/decisions/0011-spotify-provider-and-cross-provider-result-merging.md) in full (provider identity/trust order, cross-provider merging, failure isolation, config-optional-vs-fail-fast). Both are short enough to read before starting; this skill assumes you have.
- Have the vendor's own API docs open — the research questions below can't be answered from this repo alone.
- Know which existing provider is the closer template: `src/Hodnota.Infrastructure/Providers/YouTube/` (2 files, SDK-based) or `src/Hodnota.Infrastructure/Providers/Spotify/` (6 files: `SpotifyConfiguration.cs`, `SpotifyCredentials.cs`, `SpotifySearchDtos.cs`, `SpotifyAccessTokenProvider.cs`, `SpotifyApiClient.cs`, `SpotifyStreamingProvider.cs`) — Step 1 below decides which.

## Step 1: Research the vendor — never assume, always check

None of these have a fixed answer across providers; each one is a real investigation, not a checkbox to rubber-stamp.

1. **Official .NET SDK?** [decisions/0008](../../../docs/decisions/0008-youtube-search-sharepage-skeleton.md)'s rule: an official free SDK when the vendor publishes one (→ YouTube's path, ~2 files), a raw `HttpClient` via `IHttpClientFactory` otherwise (→ Spotify's path, ~6 files). This single answer determines most of the file count below. Qobuz, Tidal, Deezer, and Apple Music are not known to have official first-party .NET SDKs as of this writing — verify current status per vendor rather than trusting that assumption.
2. **Auth flow.** API key (YouTube's model) vs OAuth2 Client Credentials (Spotify's model) vs something else. No hodnota provider does per-user OAuth yet — if the vendor requires that instead of app-level credentials, that's new ground, flag it before implementing.
3. **Rate limits and quota.** Concrete numbers (requests/window, daily quota) differ per vendor and belong in this provider's own code/comments — but the *policy* for handling a limit hit is already fixed by [decisions/0011](../../../docs/decisions/0011-spotify-provider-and-cross-provider-result-merging.md)'s failure-isolation section (log-and-drop-for-this-search, not block-and-retry) and doesn't need rederiving.
4. **Can valid-looking credentials silently stop working?** Spotify's gotcha — since Feb 2026, Spotify requires the app-owner's account to have an active Premium subscription just to use the Web API in Development Mode, so correct `ClientId`/`ClientSecret` alone doesn't mean search actually works. This is what justifies Spotify's config-optional DI registration instead of the fail-fast default. Check whether the new vendor has an equivalent trap (approval-gated tiers, business-verification requirements, sandbox-vs-production key splits) before deciding fail-fast vs optional in Step 3 below — **default to fail-fast unless research says otherwise.**

   The decision is two questions, not "is it free?":

   | Question | Spotify | Qobuz | YouTube / Discogs / Tidal |
   |---|---|---|---|
   | Can any contributor get credentials self-serve? | yes | **no** (no developer portal) | yes |
   | Do correct credentials work immediately? | **no** (Premium required) | — | yes |
   | Registration | optional | optional | **fail-fast** |

   Both answers must be "yes" for fail-fast. A free plan alone is not enough (Qobuz is free to use but cannot be self-served), and free credentials that still need a paid or approved account behind them (Spotify) are not enough either.
5. **Result/metadata shape.** Genuinely new work every time: what fields does search return, how do you map them onto `StreamingSearchResult`, does the vendor expose a release-type-like signal (Spotify's `album_type` → `Hodnota.Domain.Catalog.ReleaseType`)? This is the one step with no shortcut — read the vendor's actual search-endpoint response schema (and then confirm it live, Step 1b). Also look for a version/edition field next to the title (Tidal's `version`: `null`, `""`, or free text like `Live`, `Bonus Track`, `Jungle Cruise Version Part 1`). Decide whether it goes into the displayed name using [decisions/0011](../../../docs/decisions/0011-spotify-provider-and-cross-provider-result-merging.md)'s bias — prefer a missed merge over a false merge — and record the choice in the ADR ([decisions/0013](../../../docs/decisions/0013-tidal-provider.md) appends it as `Title (Version)`).
6. **ISRC/UPC availability and exact lookup.** Map `isrc` (tracks) and `upc`/barcode (albums) onto `StreamingSearchResult.Isrc`/`Upc` whenever search returns them. Then find the vendor's exact lookup — a filter or endpoint that takes an ISRC or a barcode (Tidal: `filter[isrc]`/`filter[barcodeId]`; Deezer: `/track/isrc:`, `/album/upc:`) — and implement `SupportsLookup`/`LookupAsync` ([decisions/0014](../../../docs/decisions/0014-resolve-time-catalog-enrichment.md)); resolve-time enrichment uses it to verify the item on every provider. Vendors write the same barcode differently (12, 13 or 14 digits, leading zeros) and none normalizes it for you, so `LookupAsync` receives the forms from `CatalogKeys.BarcodeVariants`, tries them in turn, and must return only items whose own code equals one of them. A vendor with no exact lookup (YouTube) returns `false` from `SupportsLookup`, and enrichment never calls it again. Don't map a free-form barcode field that mixes real UPCs with other codes (Discogs, [decisions/0012](../../../docs/decisions/0012-discogs-provider.md)) — do that check inside `LookupAsync` instead. Confirm the lookup live (Step 1b): the docs and the real behavior have differed before.
7. **Trust-order placement.** A judgment call, not a mechanical step: how clean/structured is this vendor's own metadata (name/artist/image) compared to the providers already in `ProviderTrustOrder.Order`? Spotify ranks above YouTube because YouTube's video titles are free text and `ChannelTitle` is often a label/VEVO channel rather than the real artist. Decide where the new provider sits based on the same kind of comparison, not roadmap order or alphabetical order.
8. **Terms of service / UI presentation.** Logo usage, required attribution, linking-back rules — flagged in [docs/roadmap.md](../../../docs/roadmap.md) as a still-open, UAT-gate-deferred item that must be checked per vendor, not assumed compliant. [decisions/0011](../../../docs/decisions/0011-spotify-provider-and-cross-provider-result-merging.md) already committed the UI to neutral text (no logos, no brand colors) specifically so this future review can't force a redesign — keep following that until the review happens, regardless of what you find for the new vendor. One narrow exception has a precedent: if the vendor's terms make a credit linked back to the service a written condition of API access, it ships now as a one-line plain-text credit on `SharePage.tsx` and `SearchPage.tsx` (Discogs in [decisions/0012](../../../docs/decisions/0012-discogs-provider.md), Tidal in [decisions/0013](../../../docs/decisions/0013-tidal-provider.md)). Logos stay deferred. Do not add a credit for a style guideline that is not a stated condition.
9. **Does a legitimate access path even exist?** Some vendors have no self-serve developer portal and no confirmed-working manual request process — check whether the *entire* open-source ecosystem for this vendor relies on a workaround that conflicts with the vendor's own Terms of Use (e.g. extracting credentials from a web client instead of being issued them). If so, this is a project-level decision, not a coding step: don't default into the workaround silently. Check `CLAUDE.local.md` for an existing decision on this vendor first, or raise it before writing any code — this kind of call is deliberately kept out of the public checklist above since the reasoning can be sensitive.

## Step 1b: Probe the live API before writing any mapping code

Vendor docs can be wrong or stale (Tidal changed its search contract without notice in August 2026, and its developer portal pages could not be read without a browser). For a self-serve provider, ask the user to create the vendor app and add the credentials to the gitignored `.env.local` first (tell them the exact `X__Key=` names), then prove the real request and response shape:

1. **The agent never reads `.env.local`** — not with Read, `cat`, `grep`, or a script it runs itself (`.claude/settings.json` denies Read/`cat`; other reads get denied at the prompt). Write a throwaway probe script that the **user** runs with the `!` prefix, and put it in `C:\tmp` (an allowed directory the user's shell can reach), not in the repo.
2. **The user's `!` shell is WSL bash**, not the agent's Git Bash: paths are `/mnt/c/...`, not `C:/...` or `/c/...`, and it starts in the session's current working folder. So the script finds the repo itself (`git rev-parse --show-toplevel`, then fall back to `/mnt/c/develop/personal/hodnota` and `/c/develop/personal/hodnota`), and the command you give the user uses a path relative to their current folder (e.g. `! bash tidal-probe.sh US` when the session folder is `C:\tmp`). Use only `curl`, `grep`, and `cut` — `node`/`python` may be missing there.
3. **The script prints only status codes and non-secret fields** (`token_type`, `expires_in`, rate-limit headers). Keep the access token in a shell variable; don't save the token response to disk (if you do, delete it before finishing). Save the raw search responses next to the script for the agent to read.
4. **Read the saved responses, not the docs**, to decide the DTOs, the include/expand parameters, the result count, which fields can be null or empty, and whether parameters like a page size are really honored (Tidal ignores `page[limit]`). Probe both result types, one query with a known cross-provider match, and one without optional parameters (country/market) to learn whether they are required. Probe the exact lookup too: an ISRC and a barcode taken from a real search result, the barcode in each 12/13/14-digit form.
5. **Keep trimmed real responses** as the base of the unit-test fixtures (`XStreamingProviderSearchTests`, row 8c).
6. **Then build just the client, token provider (if any), DI registration, and a minimal provider, and check them through the running app** (Verification below) **before** writing the rest of the checklist. Finish the tests, web credit, and docs after the real API is confirmed to work.

## Step 3: DI registration — fail-fast by default

Steps 1 and 2 (`ProviderCodes`, `ProviderTrustOrder`) are pure mechanics; step 4's DI wiring has a real branch point. `AddCatalog` in `DependencyInjection.cs` registers YouTube unconditionally, throwing `InvalidOperationException` at startup if `YouTube:ApiKey` is missing — that's the default every provider should follow unless Step 1.4's research turned up a Spotify-style "valid credentials don't guarantee working access" gotcha. Only then does the provider become config-optional, guarding every one of its registrations (the credentials object, any named `HttpClient`s, the token provider, the API client, and the `IStreamingProvider` registration itself) behind `if (!string.IsNullOrEmpty(...))` the way Spotify's block does — see the guarded block immediately following YouTube's registration in `DependencyInjection.cs`'s `AddCatalog` method for the exact shape to copy if this applies. `CatalogSearchService` itself needs no change either way; it already iterates whatever `IStreamingProvider`s got registered.

For a raw-`HttpClient` fail-fast provider, copy Discogs's or Tidal's block, not YouTube's: the credentials record is built inside a `services.AddSingleton(_ => ...)` factory that throws on a missing key (so config sources applied only at `Build()`, like a test host's, are still seen), and row 4a's `Program.cs` line makes that factory run at startup.

## Verification

Two kinds of verification, and they prove different things.

**Live check (the proof it works)** — for a fail-fast (self-serve) provider this happens during the work, right after the client is wired (Step 1b.6), not at the end. With the real credentials in `.env.local`, drive a real `POST /api/catalog/search` for both types via the [run-hodnota](../run-hodnota/SKILL.md) skill — its agent-run path against `hodnota_agent`, or its "Run without Docker" SQLite path when the Postgres container can't start — and confirm the new provider's rows appear and merge with the existing providers' rows (the `platforms` list per row).

**Automated tests (the regression net)** — they never call the vendor, so they pass even when the real API shape is wrong:

```bash
dotnet build
dotnet test tests/Hodnota.Application.Tests    # ProviderTrustOrderTests, merge/key tests
dotnet test tests/Hodnota.Infrastructure.Tests # X*MappingTests, X*SearchTests, X*ApiClientTests, X*AccessTokenProviderTests, DependencyInjectionTests
dotnet test tests/Hodnota.Api.Tests            # CatalogApiFactoryTests, CatalogEndpointsTests via StubStreamingProvider
cd web && npm test && npx biome check src      # only if row 11a applied
```

Also check once that startup really fails with a clear message when a fail-fast key is missing (row 4a).

## Gotchas

- **Trust-order placement is a UI-visible decision, not just an internal ranking.** [decisions/0011](../../../docs/decisions/0011-spotify-provider-and-cross-provider-result-merging.md) ties `SharePageLink.DisplayOrder` to trust order — where you insert the new code in `ProviderTrustOrder.Order` changes the order platform links appear on every resulting share page, not just search-result-merge priority.
- **Most roadmap platforms are already pre-seeded — check before writing a migration.** `PlatformCodes.cs` and `PlatformConfiguration.cs`'s `HasData` already carry fixed-GUID seed rows for Qobuz, Tidal, Deezer, Apple Music, and Bandcamp from the original `InitialCreate` migration. Only write an `AddXPlatform` migration (mirroring `20260913185619_AddSpotifyPlatform.cs`) if the platform genuinely isn't there yet — check first, most of the time it already is.
- **`CatalogApiFactory` registers stub providers in reverse trust order on purpose.** Its own comment explains why: it's what proves `ProviderTrustOrder.Sort` is doing the sorting in endpoint tests, not registration order happening to match. Registration walks `AllProviders` reversed, so keep that list in trust order (highest first) — `CatalogApiFactoryTests` checks both the order and that every `ProviderCodes` constant is there.
- **List parameters must keep literal commas.** Tidal reads `include=tracks%2Ctracks.artists` as one unknown path and answers 400. Both `Uri.EscapeDataString` on the whole value and curl's `--data-urlencode` produce `%2C` — escape only the free-text parts (the query) and append fixed lists as-is (see `TidalApiClient`), and use `--data` for them in a probe script.
- **JSON test fixtures can't be interpolated raw strings.** JSON that closes with `}}}` fails to compile as `$$"""..."""` (CS9007) at any number of `$`. Use a plain raw string with `.Replace("@ID", id)` placeholders (see `TidalStreamingProviderSearchTests`).
- **Fail-fast is the default; config-optional is the exception, not a style choice.** Spotify's `if (!string.IsNullOrEmpty(...))` guard exists only because of a specific vendor fact (Premium-subscription requirement even with valid credentials) — don't copy that pattern reflexively for a new provider whose config, once set correctly, actually works.
- **Missing credentials block a fail-fast provider, not an optional one.** A self-serve provider's credentials take minutes to get, so get them first and probe (Step 1b) — building DTOs from docs alone risks a provider that passes every test and returns nothing live. Only a config-optional provider whose credentials genuinely can't be obtained yet (Spotify's Premium gate, Qobuz's missing portal) is built against the tests alone and merged dormant, with real credentials later.

## Troubleshooting

- **`Missing required configuration value 'X:ApiKey'.`** — thrown by `AddCatalog` at startup if you followed the default fail-fast pattern (Step 3) and the config key is unset. Expected during local dev until a real value is supplied; only silence this by going config-optional if Step 1.4's research actually found a Spotify-style access gotcha.
- **The new provider's results never appear in a merged search response, with no exception anywhere.** Check that `ProviderTrustOrder.Order` actually contains the new `ProviderCodes` constant — `RankOf` returns `int.MaxValue` for anything missing from the array, which sorts it last rather than excluding it, so "forgot to add it" looks identical to "always ranked last."
- **A raw-`HttpClient` provider passes every test but produces nothing in a real run.** Check the rate-limit path specifically: [decisions/0011](../../../docs/decisions/0011-spotify-provider-and-cross-provider-result-merging.md)'s failure-isolation model turns a thrown exception into an empty result list plus one `LogWarning`, by design — a provider silently hitting its quota looks exactly like "this provider had nothing to say" unless you check the logs.
- **A new `AddXPlatform` migration's `InsertData` fails on a unique-index violation.** Means the platform code was already seeded by `InitialCreate` — go back to the Gotcha above and check `PlatformConfiguration.cs`'s `HasData` list before writing the migration at all.
